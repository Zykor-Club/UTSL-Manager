# PacketInspector —— 管理器侧「数据包查看器」

实时查看 **UTSL 收到的所有数据包**。

## 为什么是「查看器」而不是「抓包器」

数据包只存在于**服务端进程**，管理器是另一个进程，看不到 socket。
所以抓包必须由服务端做，本插件负责**查看**：

- **服务端插件**：[UTSLServerPlugin/src/NetPacketChannel](../../../UTSLServerPlugin/src/NetPacketChannel/) —— 挂全包钩子，写环形缓冲，开 REST `/packets` 系列。
- **管理器插件**（本目录）：轮询上面那套 REST，做实时列表 / 过滤 / 统计 / 导出。

## 依赖

| 依赖 | 说明 |
|:--|:--|
| UTSL + TShock REST（`127.0.0.1:7878`） | 管理器「连接设置」里的主机/端口/令牌 |
| 服务端插件 `NetPacketChannel` | 没装就只会提示「开始抓包失败」 |
| 管理器插件 API v2 | 用到事件之外的 REST / 命令 / 指标 / 状态 |

## 构建 / 部署

~~~powershell
dotnet build -c Release
# 管理器不在默认位置时：
dotnet build -c Release -p:ManagerDir="D:\path\to\AvaloniaUTSL"
~~~

构建后自动把 `PacketInspector.dll` + `PacketInspector.manifest.json` 复制到 `<管理器目录>\plugins\`，重启管理器即可。

## 用法

1. 右侧「扩展」→「📡 数据包查看器」；**打开视图即自动开始抓包**（等价于服务端 `/packets/control?on=true`）。
2. 顶部按钮：`开始抓包` / `停止` / `清空` / `注入测试包` / `导出 JSONL` / `自动滚动`。
3. 过滤：`世界`（如 Dev）、`类型`（子串，如 PlayerUpdate）、`ID`（如 13）—— 直接下推给服务端。
4. 底部显示最近 400 行（上限），完整数据用「导出 JSONL」落盘到插件数据目录。

### 终端命令

管理器输入框敲 `!packets`：

| 命令 | 作用 |
|:--|:--|
| `!packets on` | 开始抓包 |
| `!packets off` | 停止抓包 |
| `!packets clear` | 清空服务端缓冲区 |
| `!packets top` | 把 Top 15 包类型打到终端 |
| `!packets test` | 注入 5 个合成测试包（诊断链路） |
| `!packets status` | 打印服务端抓包状态 |

### 指标 / 状态

- `抓包 · 已收到`（包）、`抓包 · 速率`（包/秒）→ 右侧「插件指标」区；
- `抓包` 状态胶囊：`监听中` / `空闲`。

## 数据字段

| 字段 | 说明 |
|:--|:--|
| `seq` | 服务端单调序号（用来做 `since` 游标、判断是否丢包） |
| `ms` | 时间戳（Unix ms） |
| `world` | 该包所属世界（UTSL 单进程多世界） |
| `who` / `player` | 来源客户端槽位 / 玩家名 |
| `id` / `type` | MessageID 数值 / 名称（**实测共 164 种**） |
| `len` | 包长度（字节） |
| `hex` | 前 N 字节（默认 64）十六进制预览 |
| `event` | 钩子时机（BeforeAllLogic / BeforeOriginalProcess） |

## 性能说明

- 服务端抓包**默认关闭**；打开后每包会做一次 hex 预览，有开销 → 建议只在排查时开。
- 服务端环形缓冲默认 4000 条（`/packets/control?buffer=` 可调，最大 50000）。
- 管理器每次轮询最多追加 150 行、保留最近 400 行，避免大流量卡 UI。

## 排错

| 现象 | 原因 |
|:--|:--|
| `开始抓包失败: ... 404` | 服务端没装 `NetPacketChannel` |
| 状态一直 `0.0 包/秒`、没有行 | 抓包期间没有玩家上线（UTSL 只在收到包时才有数据）；用「注入测试包」可自检链路 |
| 令牌错误 / 401 | 管理器的「连接设置」令牌与服务端 REST 不一致 |

## 按玩家聚合（默认模式，防刷屏）

查看器有两个模式（顶部下拉切换）：

| 模式 | 说明 | 需要先开抓包吗 |
|:--|:--|:--|
| **按玩家聚合（防刷屏）** | 每个「玩家 × 包类型」一行：首次登记 + 只涨计数 | 不需要（服务端聚合默认开） |
| 原始包流（逐包） | 逐包列表，排查单个包内容时用 | 需要（点「开始抓包」） |

聚合卡片长这样：

```
● 星梦   #3   Dev   共 1234 包 · 9 种类型   （首次 23:10:02 / 最近 23:34:12）
      #013 PlayerUpdate       x    1000     12B   首次 23:10:02   0D 03 00 ...
      #007 WorldData          x     200   1200B   首次 23:10:05   07 ...
○ #12 (未命名)   (测试)   共 50 包 · 1 种类型   ← 未在线（连接中 / 已离线残留）
```

- **● 绿** = `TShock.Players[who].Active` 为真（在线）；**○ 黄** = 连接中/未完成登录/离线残留。
- 每种类型最多显示 30 行，多的提示「还有 N 种」（导出或 `!packets who` 看全量）。
- 「只看在线」勾选后服务端会过滤掉离线槽位。
- 「导出 JSONL」在这个模式导出的其实是 **players.json**（完整聚合，含全部类型）。

### 服务端聚合规则（为什么不会刷屏）

同一个「玩家 + 包类型」**只登记一次**，之后只增加计数 → 连点 1000 次也只是一行 `x1000`。
玩家**下线立即移除**；超过 TTL（默认 300 秒）且不在线的槽位也会被回收。
详见服务端插件 README 的「玩家 × 包类型聚合」章节。

## ① 解码字段 / ④ 自动限流与封包（管理器界面）

聚合卡片里每种包类型现在会显示：

~~~
  ⛔🔍 #013 PlayerControls(PlayerUpdate)   x      8   81B  首次 23:53:32  00 00 00 …   [解码✓][拦截]
        ↳ PlayerControlData=PlayerControlData(packedValue={BitsByte}) SelectedItem=0 Position={Vector2} …
~~~

| 标记 | 含义 |
|:--|:--|
| `⛔` | 该「玩家×类型」已被自动限流（超过阈值） |
| `🚫` | 该「玩家×类型」已被手动封包（直接丢弃） |
| `🔍` | 该类型已开启字段解码 |
| `(PlayerUpdate)` | 另一套命名（TSAPI/枚举风格）作对照 |
| `↳ …` | 反序列化后的字段内容（嵌套结构展开一层） |

每行右侧两个按钮：**解码**（开/关该类型的字段解码，全局）、**拦截**（封/解该「玩家×类型」）。

### 规则工具栏

`☑ 自动限流  每 [1000] ms 内超过 [120] 包 → [只告警/丢包/踢下线]  [应用规则] [清空规则]`

- 下面是**违规行**：最近 6 条违规（谁、什么包、当时多少包、采取了什么动作）+ 累计丢包数。
- 「清空规则」= 关限流 + 清封包名单 + 清解码。

### 命令

| 命令 | 作用 |
|:--|:--|
| `!packets rules` | 打印当前规则 / 受限对 / 封包对 / 解码列表 |
| `!packets limit on` 或 `off` | 开/关自动限流（阈值用界面上的） |
| `!packets block <槽位> <包ID>` | 封掉某玩家的某类型 |
| `!packets unblock <槽位> <包ID>` | 解除 |
| `!packets decode <包ID>` | 开启该类型字段解码 |

### 注意

- 解码是**有成本**的（注册过的类型每个包都要反序列化）→ 只对真正要看的类型开。
- 限流是**自动动态注册**的：平时零成本，只有某个「玩家×类型」真的超阈值了，才注册该类型并开始丢包；超时释放后会自动反注册。

## ② 方向（C→S / S→C）与 ⑤ 关注名单

- 工具栏有**方向**下拉：`全部` / `↓ C→S 收到` / `↑ S→C 发出`（下推给服务端 `?dir=`）。
- 卡片标题带方向：`↓ C→S  ○ Alice #60 …` / `↑ S→C  ○ Bob #61 …`；原始包流每行前面也有 `↓`/`↑`。
- 拦截按钮作用于**该卡片的方向**（`/packets/block?dir=&who=&id=`）。
- 违规行左侧显示**关注名单**：`关注名单 [Alice,Bob,Carol] · 违规 4 条 …`。

| 命令 | 作用 |
|:--|:--|
| `!packets watch <名字>` | 加入关注名单（这些人即使没开全局抓包也会单独抓全量原始包） |
| `!packets watch- <名字>` | 移出 |
| `!packets watchclear` | 清空 |
| `!packets config` | 打印配置文件路径 / 关注名单 / 抓包开关 / 解码 / 封包 |

> S→C 只看得到十六进制（不走反序列化），解码仅对 C→S 有效。

## 解码失败标记（❌）

有些包类型的 TrProtocol 定义跟真实线格式不一致（例如 `#016 TileChange`、`#017 MenuSunMoon` 真实是 16 位坐标），
这些类型解不出来，服务端会把它们加入黑名单，管理器里显示为：

~~~
  ·❌ #017 MenuSunMoon(Tile) x 14 9B … [解码✗][拦截]
~~~

- `❌` / `解码✗` = 该类型无法解码（不是功能故障，是定义不符）；
- `🔍` / `解码✓` = 正常解码，卡片里会多一行 `↳ 字段…`；
- 解码**不再注册类型处理器**，所以开解码不会影响游戏（之前会打断 `TileChange` 这类包的处理，已修复）。

## ↑ S→C 卡片的显示约定（⚠仅类型/计数）

S→C 走 `NetMessage` 层，**只有类型和目标、没有线缆字节**，所以：

~~~
↑ S→C ⚠仅类型/计数   ○ 星梦   #0   Dev
  · #004 SyncPlayer           x      12       —     首次 00:26:30              [拦截]
~~~

- 长度显示 `—`、hex 不显示；
- **没有「解码」按钮**（无字节可解），「拦截」保留（服务端 `ContinueExecution=false` 真能拦）；
- 顶部的「在线 N 人」已按**槽位去重**（之前同一人在 C→S/S→C 各算一次，会显示成「星梦, 星梦」）。
